Every box (Local / Edge / Cloud) is its own small waiting-line with a fixed amount of work it can do per time-step — that rule was proven correct in Step 1 and reused everywhere. task.py defines the task object that flows through every box.

A task that isn't finished simply waits and tries again on the next time-step — nothing is lost, and no department can ever exceed its own capacity.

This step builds the foundation the rest of the project stands on. Three hospital departments — Emergency, ICU, and General Ward — are each modelled as an EdgeNode: a small computer with a fixed amount of processing power available per time-step. Tasks are added one at a time and wait in a first-in-first-out queue. On every tick of the simulation clock, a node works through its queue from the front, spending its capacity on whichever task is waiting; if a task needs more work than the remaining capacity allows, it is left partially finished and automatically continues from where it left off on the next step.

No intelligence or decision-making exists yet — the goal here is only to prove the basic bookkeeping is correct before anything more advanced is added on top. Five automated tests confirm that tasks are never lost, capacity is never exceeded, departments never interfere with one another, and invalid input is rejected with a clear error message.

def step(self, current_time: int) -> None:
    available_capacity = self.capacity
    still_in_queue = []

    for task in self.queue:
        if available_capacity <= 0:
            still_in_queue.append(task)   # no compute left, task simply waits
            continue

        work_done = min(available_capacity, task.remaining_demand)
        task.remaining_demand -= work_done
        available_capacity -= work_done

        if task.is_complete:
            task.completion_time = current_time
            self.completed_tasks.append(task)
        else:
            still_in_queue.append(task)   # partially done, carries over

    self.queue = still_in_queue

Step 1 required every task to be added by hand. Real hospitals do not work that way — patients and workloads arrive on their own, unpredictably, but around some average rate. This step introduces the MedicalTaskGenerator, which reproduces that behaviour using a Poisson process: a standard statistical model for "how many random events happen in a fixed interval." Each department and priority combination — for example, Critical cases in the ICU — runs its own independent Poisson process, because a Critical event in the ICU is naturally far more likely than the same event in the General Ward.

Whenever a task is generated, its workload is also drawn randomly, from a range that matches its priority level. Once created, the task is handed to the exact same simulator built in Step 1, so every queueing and capacity rule already proven continues to apply unchanged. The same random seed always reproduces the identical sequence of tasks, which matters for debugging and for defending results later. The specific arrival-rate numbers used right now are clinically-plausible placeholders, pending approved access to the MIMIC-IV clinical dataset — only those numbers will change later, not this code.

All three tiers then process the task using the same proven FIFO + capacity mechanics from Step 1 — Cloud additionally makes the task wait network_delay (2) steps "in transit" before it may start.

Every task now faces a choice of where it gets executed, not just when. The TaskRouter looks only at a task's compute_demand and, using two configured thresholds, sends it to one of three tiers: Local (a tiny on-device resource — instant, but very limited capacity), Edge (the department's own node, unchanged from Steps 1 and 2), or Cloud (one powerful resource shared by the entire hospital, reached only after a configurable network delay). This mirrors the real "offloading" trade-off found in edge-computing systems: keep work close and fast, or send it somewhere more powerful but slower to reach.

It is important to be explicit that this routing rule is fixed and hand-written, not learned. Its only job is to prove that the three-tier queueing, capacity, and network-delay mechanics behave correctly before any intelligence is introduced. From Step 7 onward, a reinforcement-learning agent will occupy this exact decision point and learn to route tasks more effectively than this simple rule. Just as importantly, the original Step 1/2 behaviour was left completely untouched — add_task() still always goes straight to the Edge node — so nothing earlier in the project could break by adding this feature.

def choose_tier(self, compute_demand: float) -> str:
    if compute_demand <= self.local_threshold:
        tier = "Local"
    elif compute_demand <= self.edge_threshold:
        tier = "Edge"
    else:
        tier = "Cloud"
    return tier
